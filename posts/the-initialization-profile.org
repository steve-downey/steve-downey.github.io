* About this document

Every code block in P4222R3 (Stroustrup, 2026-10-22, "An initialization profile") is reproduced below, compiled under the profile on the two implementations the paper cites as "tested nightly" [Impl1, Impl2], with what the paper says should happen beside what does. Where a block needed scaffolding to be a translation unit (a definition of =X=, a declaration of =my_malloc=, a fix to a typo) the addition is marked in a comment; lines added to probe a consequence the paper does not spell out are marked =// added=.

The whole set was rechecked on 2026-11-14: every listing recompiled and compared, and each claim in the prose that goes beyond a listing tried with a small program of its own. The listings all stood. Some of the prose did not, and where a passage changed it carries a bracketed note beginning "Revised 2026-11-14" that says what the first version said.

The examples are grouped by how badly the paper and the implementations disagree, worst first: rejected by both compilers where the paper says OK; rejected by Clang where the paper says OK; accepted by Clang where the paper says error; GCC alone differing; and the examples where both compilers agree with the paper. Within a group the examples follow the paper's order unless noted. The [[#summary-table][summary table]] at the end lists all 36 in the paper's order.

Of 36 examples, the two implementations give the same verdicts on 20 (and nearly so on 1 more); on the other 15 they disagree with each other, in most cases on lines the paper annotates. [Revised 2026-11-14: the first version had 18, 2 and 16. In [[#label-construct-at][§5.3 Label]] and [[#classes-without-ctors][§5.4 classes without constructors]] GCC's extra error against the type turned out to be its report of the same line Clang rejects.] Nine of the paper's examples are rejected by both compilers on a line the paper marks OK; they are the first group below, led by the §4.7 =Vector= the paper calls "guaranteed free from initialization errors". In two of the nine ([[#user-uninitialized-fill][§4.9 uninitialized_fill]], [[#arrays][§5.5 arrays]]) the paper's own text contradicts the annotation.

Three recurring causes account for most of the differences:

1. GCC does not know the standard library. =malloc= returns initialized memory to it ([[#malloc-calloc][§4.3 malloc/calloc]] note, [[#vector-example][§4.7 Vector]], [[#malloc-new-mix][§4.11 malloc/new]], [[#classes-exposing-uninit][§5.3 exposing uninitialized]]), and so does =new int= ([[#unique-ptr-new][§4.9 unique_ptr/vector]]); a second =construct_at= or =destroy_at= of the same object goes unnoticed ([[#lifetimes-destroy-at][§4.6 destroy_at]]); =std::uninitialized_fill= and =free= are unannotated and so reject marked arguments ([[#vector-example][§4.7 Vector]]). Clang knows these by builtin ID. [Revised 2026-11-14: the first version said =construct_at= and =destroy_at= were unmodelled on GCC, and listed the §4.9 example under =malloc=, which it does not call. =construct_at= is modelled: GCC accepts =std::construct_at(&x, 10)= on an =[[uninit]]= local and a read of =x= after it, where the same address passed to an unannotated function template is an error. What GCC does not do is notice the second one.]
2. GCC implements =[[ref_to_uninit]]= on pointers and references only: not on class-type handles ([[#lifetimes-construct-at][§4.6 construct_at]], [[#attribute-placement-settled][Appendix settled forms]]), not on a read through a marked return value ([[#class-slot][§4.5 Slot]]), and not on a reference bound to a local ([[#pointer-reference-flavors][§4.3 f1/f2/g]]). Clang implements all of these. [Revised 2026-11-14: the first version said "not on return types". GCC does check where a marked returned pointer is stored ([[#malloc-calloc][§4.3 malloc/calloc]]); it is a read through the returned pointer or reference that it lets by. The Appendix placement example was also cited for references to locals, and it has none.]
3. The attribute vocabulary has forked: the paper's =[[must_init]]= is unknown to Clang, which implements =[[now_init]]=; GCC implements =[[must_init]]= but on the parameter rather than in the paper's function position ([[#must-init][§4.2 must_init]], [[#attribute-placement-settled][Appendix settled forms]]). =std::now_init= ships in GCC's =<utility>= and nowhere in Clang's library ([[#now-init-span][§1.4 now_init to a span]]).

* Rejected by both implementations where the paper says OK

The paper marks a line OK, or presents the form as the sanctioned one, and both compilers reject it. GCC's branch is a quick proof of concept and its verdict alone settles little; when Clang, the fuller implementation, and GCC agree in rejecting, the example does not work as written. The =Vector= comes first because the paper's claim for it is the strongest. In the last two the paper's own text contradicts the annotation the compilers reject.

** §4.7 — The Vector example
:PROPERTIES:
:CUSTOM_ID: vector-example
:END:

#+BEGIN_SRC C++ -n
[[profiles::enforce(std::init)]];
#include <memory>
#include <cstdlib>
// scaffolding: std::now_init exists in the GCC branch's <utility>; the Clang branch recognizes
// std::now_init by name but ships no declaration, so one is supplied for it
#include <utility>
#ifdef __clang__
namespace std { template<class T> T* now_init(T* p [[ref_to_uninit]]); }
#endif
// scaffolding the sketch assumes
struct Bad_index {};
void* my_malloc [[ref_to_uninit]] (std::size_t);
using std::uninitialized_fill; using std::uninitialized_move; using std::now_init;
using std::malloc; using std::free; using std::construct_at;

template<class T>
struct Vector_memory {
    T* elem [[ref_to_uninit]];
    int no_of_elem = 0;
    int no_of_slots = 0;
    Vector_memory(int ne, int ns)
        : elem{ (T*)my_malloc((ne + ns) * sizeof(T)) },
          no_of_elem{ ne },
          no_of_slots{ ns }
    { }
    ~Vector_memory() { free(elem); }
};

template<class T>
class Vector {
    Vector_memory<T> mem;
public:
    Vector() {}
    Vector(int ne, int ns, const T& val = T{})
        : mem{ ne,ns }
    {
        // assume that uninitialized_fill() knows about [[ref_to_uninit]]:
        uninitialized_fill(mem.elem, mem.elem + ne, val);
    }
    T& operator[](int i)    // note the use of now_init()
    {
        if (0 <= i && i < mem.no_of_elem)
            return *now_init(mem.elem + i);   // this slot has been initialized
        throw Bad_index{};
    }
    ~Vector() { destroy(now_init(mem.elem), mem.no_of_elem); }
    void reserve(int newsz)
    {
        int n = mem.no_of_elem;
        if (newsz <= n + mem.no_of_slots) return;
        T* p [[ref_to_uninit]] = (T*)malloc(newsz * sizeof(T));
        T* old_elem = now_init(mem.elem);
        uninitialized_move(old_elem, old_elem + n, p);
        destroy(old_elem, n);
        free(mem.elem);
        mem.no_of_slots = newsz - n;
        mem.elem = (T*)p;
    }
    void push_back(const T& x)
    {
        if (mem.no_of_elem == mem.no_of_slots)
            reserve(mem.no_of_elem == 0 ? 8 : 2 * mem.no_of_elem);
        construct_at(mem.elem + mem.no_of_elem, x);
        ++mem.no_of_elem;
        --mem.no_of_slots;
    }
    void destroy(T*, int);
};

int use()
{
    Vector<int> v(2, 2, 7);
    v.push_back(1);
    return v[0];
}
#+END_SRC

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=23][§4.7, page 23]]:

#+begin_quote
Here is a much-simplified sketch of such a function template [the =Vector_memory= above].

=Vector_memory= knows only about uninitialized memory.

[The =Vector= class above.]

Here, I have assumed that =malloc()=, =free()=, etc. is known to the initialization profile. If not, equivalent functions with slightly different names that do use the initialization attributes must be used (§4.4).

The main point here is that the code is quite conventional (for this kind of C++ code). It is guaranteed free from initialization errors except for the call of =now_init()= call in the subscript operator. It is only called from within an initialized range but verifying that statically would be expensive and in some similar cases impossible. Having =now_init()= saves the user from suppressing the profile and offers an easy-to-spot point for code review.
#+end_quote

The sketch is made compilable with the smallest edits: =Int= to =int=, a =Bad_index= type, a declaration of =my_malloc=, =std::= qualification, and the member =destroy= declared as the paper has it. The function =use= is added. Expected: accepted.

*** What happens

The paper says the sketch "is guaranteed free from initialization errors except for the call of now_init()". Clang rejects line 57, =mem.elem = (T*)p;= in =reserve=: after =uninitialized_move= into =p=, =p='s referent is initialized, and a =[[ref_to_uninit]]= member may not be made to refer to initialized memory. =elem= refers to a /mixed/ range, and the design has no marker for one. That is the design's central problem, and it is one line long. GCC reports five errors on four lines, all for the same reason: the standard library is not annotated. [Revised 2026-11-14: was "rejects five lines".] =(T*)malloc(...)= into a marked pointer is rejected (GCC treats =malloc='s result as initialized), =free(elem)= is rejected twice ("its parameter is not marked =[[ref_to_uninit]]="), and =std::uninitialized_fill(mem.elem, ...)= is rejected on both iterator arguments. The paper's comment "assume that uninitialized_fill() knows about =[[ref_to_uninit]]=" is exactly the assumption that fails.

** §1.4 — Range-for as initialization (aar6)
:PROPERTIES:
:CUSTOM_ID: range-for-init
:END:

#+BEGIN_SRC C++ -n
[[profiles::enforce(std::init)]];
int aar6_test()
{
    int aar6 [[uninit]] [10];
    for (int& x : aar6) x = 0b1010101010101010;
    return aar6[3];   // added: is the loop credited as initialization?
}
#+END_SRC

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=8][§1.4, page 8]]:

#+begin_quote
Range-for loops be are often simple to validate. For example [the loop above]. To allow that, the initialization profile would have to recognize the loop as an initialization, verify that the loop body really is initialization, and that the loop really complete.
#+end_quote

The paper implies this should be accepted. A read after the loop is added to see whether the loop is credited as initialization.

*** What happens

Neither compiler recognizes the range-for as an initialization. Clang rejects the loop header on line 5 (the implicit =__range= reference binds uninitialized memory unmarked) and the read on line 6. GCC rejects the same header twice (once as a marker mismatch, once as address-taken-before-initialized) and the read. So the case the paper calls "simple to validate" is a hard error on both. The sanctioned way to fill the array is =std::uninitialized_fill= over the whole range, and that works on Clang only: GCC rejects =std::uninitialized_fill(aar6, aar6 + 10, 0)= and the =std::ranges= form as well, its library not being annotated. [Revised 2026-11-14: the first version gave =std::uninitialized_fill= as the way out without having tried it on GCC.]

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=9][§1.4, page 9]]:

#+begin_quote
Initialization too complex for the analyzer to recognize is best avoided but if really necessary can be handled by suppressing the initialization profile or using by (the unverified) =now_init()= (§4.6). For example [the function above]. Such suppression is an obvious target for code review and more advance analysis.
#+end_quote

Expected: accepted; =s= is usable, and =aar10= should not be used directly afterwards. =now_init= is spelled =std::now_init=, since §8.5 adds it to the standard library.

*** What happens

First, =std::now_init= does not exist in either standard library as shipped: the GCC branch adds it to =<utility>= (taking =[[must_init]]=), the Clang branch recognizes the name =std::now_init= but provides no declaration, so the scaffolding declares one for Clang. With that, both compilers reject line 16, the "any initialization technique" call, because passing =aar10= to an unannotated =X*= parameter is itself the violation. The =now_init= line and the use of =s= are accepted by both. The example works only if the elided "…" is itself profile-clean, which for anything the paper would call "too complex for the analyzer" it will not be; =now_init= launders the /result/ but not the /route/.

** §5.3 — Label lab1 =[[uninit]]=; construct_at(&lab1, x, y, z)
:PROPERTIES:
:CUSTOM_ID: label-construct-at

#+BEGIN_SRC C++ -n
[[profiles::enforce(std::init)]];
#include <string>
#include <memory>
using std::string;

struct Label {
    string name;
    string address;
    int code;
};

void tst(const char* n, const char* a, int c, const char* x, const char* y, int z)
{
    Label lab0 { n, a, c };
    Label lab1 [[uninit]];
    // ...
    std::construct_at(&lab1, x, y, z);
}
#+END_SRC

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=33][§5.3, page 33]]:

#+begin_quote
For uninitialized class objects, we’ll have to use =construct_at()= rather than simple assignment to do the initialization. For example [the code above].
#+end_quote

Expected: accepted.

*** What happens

Both reject =Label lab1 [[uninit]];=: the type has non-trivial default initialization (two =std::string= members), so it cannot be marked. GCC's second error, against the =Label= type ("constructor does not initialize member 'Label::code'"), is the same line again: it comes with a note that the synthesized default constructor was first required at =lab1=, and =Label lab0 { n, a, c };= compiles on GCC by itself. The idiom the paper is illustrating, =construct_at= over an object whose string members are already alive, is a double construction: no destructor runs for the strings that were there. With both still empty, libstdc++ loses nothing; once one of them owns heap memory it leaks, which is what the [[https://godbolt.org/z/szzP1zWxe][runtime demo]] shows under AddressSanitizer. Both implementations refuse to let it be spelled. [Revised 2026-11-14: the first version said GCC rejects the =Label= type itself, so that =lab0= could not be declared, and said the idiom "leaks when run" without saying that the demo first assigns a long string to =lab1.name=.]

** §5.4 — Label: mixed members, the =[[uninit]]=-member repair, and the all-initialized form
:PROPERTIES:
:CUSTOM_ID: label-uninit-members
:END:

#+BEGIN_SRC C++ -n
[[profiles::enforce(std::init)]];
#include <string>
using std::string;

struct Label {
    string name;
    string address;
    int code;
};

struct Label2 {             // "OK, but not for static objects"
    string name [[uninit]];
    string address [[uninit]];
    int code;
};

struct Label3 {             // "OK"
    string name;
    string address;
    int code = 0;
};

void f(const char* n, const char* a, int c)
{
    Label lab0 { n, a, c };     // OK
    Label lab1;                 // error: lab1.code uninitialized
    Label lab2 [[uninit]];      // error: lab1.name and lab1.address are default initialized
    Label2 lab2b [[uninit]];    // paper: would have been OK
    Label3 lab3;                // OK
}
#+END_SRC

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=34][§5.4, page 34]]:

#+begin_quote
Classes with a mix of initialized and uninitialized members give errors unless immediately initialized [the =Label=, =lab0=, =lab1= and =lab2= above].

The =lab2= definition would have been OK if =Label= had been defined as [the =Label2= above, which the paper comments “OK, but not for static objects”].

Usually, it would be better to ensure that either all members are default initialized or none [the =Label3= above, which the paper comments “OK”].
#+end_quote

The paper's three definitions of =Label= are renamed =Label=, =Label2=, and =Label3= so they fit in one TU, and =lab2b= is added to declare the =[[uninit]]= object the paper says the repaired definition permits. Expected: =lab0= OK; =lab1= error (=lab1.code= uninitialized); =lab2= error (=name= and =address= are default initialized); =lab2b= OK; =lab3= OK.

*** What happens

=lab1= and =lab2= are rejected by both, as the paper says (GCC reports =lab1='s problem against the type =Label= rather than the variable). The repair the paper offers, =Label2= with =string name [[uninit]]=, is rejected by both at the member declarations: =[[uninit]]= cannot be put on a =std::string= because default-initialization does not leave it uninitialized. So =Label2 lab2b [[uninit]]=, which the paper says "would have been OK", is an error on both, and there is no spelling in either implementation for leaving a member that has a default constructor uninitialized. A class that mixes an initialized member with an =[[uninit]]= scalar or array member is accepted by both ([[#class-slot][§4.5 Slot]], [[#classes-exposing-uninit][§5.3 =X_annotated=]]). [Revised 2026-11-14: the first version said there was no spelling for a class with some members initialized and some not, which those two examples contradict.] =Label3= (=int code = 0=) is accepted by both.

#+begin_quote

- =int* arr2 [[ref_to_uninit]] [10];= Plausible: the attribute is just after the name as in variable definitions.

** §5.2 — The three alternatives: nullptr pseudo-initialization, unique_ptr, default-constructed strings
:PROPERTIES:
:CUSTOM_ID: member-alternatives
:END:

#+BEGIN_SRC C++ -n
[[profiles::enforce(std::init)]];
#include <memory>
#include <string>
constexpr int sys_max = 1000;
void error(int);

class X1 {
    int* p = nullptr;
    int x;
public:
    X1(int v) : x{v}
    {
        if (v < 0 or sys_max <= v) error(v);
        p = new int(v);
    }
};

class X2 {
    std::unique_ptr<int> p;
public:
    X2(int x) : p{std::make_unique<int>(x)} {}
};

class X3 {
    std::string s1;
    std::string s2;
public:
    X3(const char* ss1, const char* ss2) : s1{ss1} { s2 = ss2; }
};
#+END_SRC

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=31][§5.2, page 31]]:

#+begin_quote
Often, using a “pseudo initialization” is a better choice. For example [the =X1= above].

In most such cases, the optimizer can eliminate the redundant initialization.

Alternatively, we could use =now_init()= or suppression to expose that unverified =p= to users.

Often, an even better alternative is to use a member of a type that performs its own checks rather than more primitive types. For example [the =X2= above].

Default construction works as ever. For example [the =X3= above].

The use of the member initialization (for =s1=) is preferred to the assignment (of =s2=) as being more readable and more efficient unless the optimizer is smart enough to eliminate the default initialization of =s2=.
#+end_quote

All three are presented as acceptable. Expected: accepted. The paper's =make_unique(x)= is missing its template argument; =make_unique<int>(x)= is used.

** §5.4 — Classes without constructors: S s1..s4
:PROPERTIES:
:CUSTOM_ID: classes-without-ctors
:END:

#+BEGIN_SRC C++ -n
[[profiles::enforce(std::init)]];
#include <string>
using std::string;
struct S { int x; string s; };

void f()
{
    S s1 = {1, "foo"};  // OK
    S s2 = {1};         // OK, s2.s defaults to ""
    S s3;               // error: s3.x uninitialized
    s3.x = 1;
    s3.s = "foo";
    S s4 [[uninit]];    // error: s4.s is default constructed
    s4.x = 1;
    s4.s = "foo";
}
#+END_SRC

*** What the paper says

P4222R3 [[https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf#page=33][§5.4, page 33]]:

#+begin_quote
When defining objects of classes without constructors we must initialize all members in their definitions. For example [the function above].

The member =s4.s= is a =string=, and =string= has a default constructor. That means that =S s4 [[uninit]];= declares =s4.s= as both initialized and uninitialized. That’s an error (even before we start considering delayed initialization).

Immediate initialization is simpler and clearer.

Don’t introduce a variable until you have an initializer for it.
#+end_quote

Expected: =s1= OK; =s2= OK (=s2.s= defaults to =""=); =s3= error (=s3.x= uninitialized), followed by member assignments; =s4= error (=s4.s= is default constructed), followed by member assignments.

*** What happens

Clang: =s3= rejected as the paper says; =s4 [[uninit]]= rejected because =S= default-initializes (the paper's reason, differently phrased); and then both member assignments to =s4= are rejected too. GCC: =s4= rejected for the same reason. =S s3;= is reported not at line 10 but against the type at line 4 ("constructor does not initialize member 'S::x'"), with a note that the synthesized default constructor was first required at line 10. That is the paper's error on =s3=, reported where the constructor is and not where it is used; =s1= and =s2= compile on GCC by themselves. GCC says nothing about the member assignments to =s4=. [Revised 2026-11-14: the first version read the line-4 error as GCC rejecting the type =S= however it is used, =s1= and =s2= included, and filed this example with the ones where GCC alone diverges. Compiling =s1= and =s2= without =s3= shows otherwise, and the example has moved here.]

* Not reproduced

Three of the paper's code fragments are not translation units under any reasonable completion and are omitted:

- §4.6's =vector<Slot> v; vector<Live> live_slot; ... if (live_slot[x]==Live.init) { int xx = v[x]; ... }=: =Live.init= is not C++, and =v[x]= is a =Slot=, not an =int=; the paper offers it as a sketch of a run-time technique the profile cannot verify.
- §4.10's concept-based overload set (=template<Pointer_to_uninit T> int f(T* p)=): the paper itself calls it an "unattainable ideal", since "the information for doing that is not available to a concept".
- §1's opening figure of "errors caught by the GCC and Clang implementations" is an image in the PDF, not text; its content is covered by [[#uninit-rules][§4.1 rules]].

* Method

Each source was compiled through Compiler Explorer's API on 2026-10-25 against the two compilers above and the diagnostics recorded; the links were then created with CE's shortener using a full layout state (editor; per compiler, a compiler pane over an output pane) and each link's stored source checked against the compiled source. Diagnostics shown are trimmed of ANSI colour, source-echo and caret lines, context lines and notes, Clang's trailing warning-flag name, the "under profile 'std::init'" (Clang) or "under the 'std::init' profile" (GCC) that every message carries, and the "aka" expansion after a type name. The =std::uninitialized_fill= signature in the §4.7 listing is cut to =(...)=, and four listings are in line order where the compiler emitted them otherwise. Nothing else is edited. [Revised 2026-11-14: the first version listed fewer trims than were made.]

On 2026-11-14 all 36 sources were compiled again and each listing compared with the fresh output, and each link's stored source and compiler settings compared with the post. Everything matched. The claims in the prose that a listing does not show by itself were then each tried with a small program of their own; where one failed, the passage is revised and says so.
